## 前言

在前幾篇文章中，我們深入探討了 Modbus 協定——從暫存器讀寫、資料型別解碼，到完整的設備抽象層。Modbus 是工業控制領域的「通用語言」，簡單、穩定、無所不在。但當你開始接觸智慧電網（Smart Grid）、變電站自動化（Substation Automation）或大型儲能系統（ESS）時，你會發現 Modbus 的「簡單」反而成了限制。

想像一下：你負責一個儲能案場，裡面有 PCS（功率轉換系統）、BMS（電池管理系統）、電表、太陽能逆變器等十幾種設備。每家廠商的 Modbus register map 都不一樣，地址 40001 在 A 廠是有功功率，在 B 廠是無功功率。你得維護一堆「地址對照表」，而且這些表沒有任何自描述能力——純粹是一組數字。

IEC 61850 正是為了解決這個問題而生的。

## 1. IEC 61850 概觀：次世代變電站標準

IEC 61850 的全名是《Communication Networks and Systems for Power Utility Automation》，由 IEC（國際電工委員會）制定。它不只是一個通訊協定，更是一套**完整的資料模型標準**。

### 設計目標

| 目標 | 說明 |
|------|------|
| 互操作性（Interoperability）| 不同廠商的設備可以直接溝通，不需要客製化映射 |
| 自描述資料模型 | 設備本身攜帶語義資訊，而非只有原始數值 |
| 高效能即時通訊 | 支援毫秒級的保護信號傳輸 |
| 面向未來 | 可擴展的物件導向架構 |

### 歷史脈絡

IEC 61850 最初（2003 年第一版）聚焦於變電站自動化。但隨著分散式能源（DER）、儲能系統、微電網的蓬勃發展，它的適用範圍不斷擴大：

- **IEC 61850-7-420**：分散式能源（DER）專用模型
- **IEC 61850-90-7**：逆變器功能模型（與 IEEE 1547 呼應）
- **IEC 61850-90-12**：廣域網路通訊

對於後端工程師來說，理解 IEC 61850 最直覺的方式是：**把它想成工業控制的 GraphQL Schema**。Modbus 像是 REST API 中直接操作記憶體地址的低階介面，而 IEC 61850 則提供了一套型別安全、語義清晰的資料存取層。

## 2. 資料模型階層：Server → Logical Device → Logical Node → Data Object → Data Attribute

IEC 61850 的核心是它的**語義資料模型**。這個模型是階層式的，每一層都有明確的語義意義。

### 完整階層

```
Server (物理設備/IED)
└── Logical Device (邏輯設備)
    └── Logical Node (邏輯節點 — 功能單元)
        └── Data Object (資料物件)
            └── Data Attribute (資料屬性 — 實際值)
```

讓我們從上到下逐層理解：

### 2.1 Server（伺服器）

Server 對應一個**物理的智慧電子裝置（IED, Intelligent Electronic Device）**。一台 IED 就是一個 Server。類比到軟體世界，Server 就像一個微服務實例。

### 2.2 Logical Device（邏輯設備）

一個 Server 可以包含多個 Logical Device。Logical Device 是功能分群的容器。例如，一台 PCS 的 IED 可能包含：

- `CTRL`：控制功能
- `MEAS`：量測功能
- `PROT`：保護功能

### 2.3 Logical Node（邏輯節點）

這是 IEC 61850 最重要的概念。每個 Logical Node 代表一個**獨立的功能單元**，以標準化的前綴命名：

| 前綴 | 類別 | 範例 |
|------|------|------|
| `MMXU` | 量測 | 三相電壓、電流、功率 |
| `XCBR` | 斷路器 | 開關狀態與控制 |
| `CSWI` | 開關控制 | 開關指令 |
| `DRCS` | DER 控制 | 分散式能源控制 |
| `DBAT` | 電池 | 電池狀態與管理 |
| `DSCH` | 排程 | 充放電排程 |
| `GGIO` | 通用 I/O | 通用輸入輸出 |

每個 Logical Node 的名稱是**標準化**的。這意味著無論是哪家廠商的 PCS，它的量測功能都叫 `MMXU`，電池狀態都叫 `DBAT`。

### 2.4 Data Object（資料物件）

Data Object 是 Logical Node 內的具體資料項。例如 `MMXU` 中：

- `TotW`：總有功功率
- `TotVAr`：總無功功率
- `PhV`：相電壓
- `Hz`：頻率

### 2.5 Data Attribute（資料屬性）

Data Attribute 是最底層，存放實際的值。每個 Data Object 可以有多個 Attribute：

- `mag.f`：量測值（浮點數）
- `q`：品質標誌（資料是否有效）
- `t`：時間戳記

### 完整的存取路徑範例

```
MyPCS/CTRL/DRCS1.DERCtlP.setMag.f = 50.0
│      │    │     │       │      │
│      │    │     │       │      └── Data Attribute (浮點值)
│      │    │     │       └── Data Attribute (設定值)
│      │    │     └── Data Object (DER 功率控制)
│      │    └── Logical Node (DER 控制, 實例1)
│      └── Logical Device (控制)
└── Server (PCS 設備)
```

這就像一個完整的 URL path：`/MyPCS/CTRL/DRCS1/DERCtlP/setMag/f`。每一段都有語義意義，而不是一個無意義的暫存器地址。

## 3. 通訊服務：MMS、GOOSE、SMV

IEC 61850 定義了三種通訊機制，針對不同的使用場景最佳化。

### 3.1 MMS：客戶端-伺服器模式

**MMS（Manufacturing Message Specification, ISO 9506）** 是 IEC 61850 的基礎通訊機制，基於 TCP/IP。

```
┌─────────────┐        TCP/IP         ┌─────────────┐
│   SCADA /   │ ──── MMS Request ───→ │    IED      │
│   Client    │ ←── MMS Response ──── │   (Server)  │
└─────────────┘                        └─────────────┘
```

MMS 用於：
- **讀取**（GetDataValues）：讀取資料物件的值
- **寫入**（SetDataValues）：設定控制參數
- **報告**（Report）：訂閱資料變化通知
- **瀏覽**（GetDirectory）：探索設備的資料模型

MMS 的特性跟 Modbus TCP 很像——都是 request/response 模式。但 MMS 操作的是有語義的資料物件，而不是原始暫存器。

```
# Modbus 讀取有功功率
client.read_holding_registers(address=40001, count=2, slave=10)
# 你得知道 40001 是有功功率，Float32，Big-Endian...

# IEC 61850 MMS 讀取有功功率
client.read("MyPCS/CTRL/MMXU1.TotW.mag.f")
# 路徑本身就說明了：PCS 的量測節點的總有功功率
```

### 3.2 GOOSE：多播事件（保護信號，< 4ms）

**GOOSE（Generic Object Oriented Substation Event）** 是 IEC 61850 的殺手級功能。它直接運行在 **Layer 2（Ethernet）**，跳過了 TCP/IP 堆疊，實現極低延遲的多播通訊。

```
┌──────────┐    Ethernet Multicast     ┌──────────┐
│  IED A   │ ─── GOOSE Message ──────→ │  IED B   │
│ (保護)    │ ─── GOOSE Message ──────→ │  IED C   │
└──────────┘                            └──────────┘
```

GOOSE 的核心特性：

| 特性 | 說明 |
|------|------|
| 延遲 | < 4ms（典型 < 1ms） |
| 傳輸層 | Layer 2 Ethernet（非 TCP/IP） |
| 模式 | Publisher/Subscriber 多播 |
| 可靠性 | 重複傳送 + 序號機制 |
| 用途 | 保護跳脫信號、聯鎖邏輯 |

為什麼 GOOSE 這麼快？因為它跳過了 TCP 的握手、確認、重傳等機制。在電力保護場景中，一個斷路器跳脫信號如果延遲超過 4ms，可能導致設備損壞甚至安全事故。GOOSE 透過在 Ethernet 層直接多播，並以遞增頻率重複發送（第一次立刻發、第二次隔 1ms、第三次隔 2ms、逐漸拉長）來兼顧速度和可靠性。

```
# GOOSE 跳脫信號時序
t=0ms   →  GOOSE 發送 (斷路器跳脫!)
t=1ms   →  GOOSE 重發
t=3ms   →  GOOSE 重發
t=7ms   →  GOOSE 重發
t=15ms  →  GOOSE 重發
...
t=1000ms → GOOSE 穩態重發（心跳）
```

### 3.3 SMV：取樣值傳輸

**SMV（Sampled Measured Values）** 用於傳輸高速取樣的電氣量（電壓、電流波形）。取樣率可達 4800 samples/sec（60Hz 系統下每週期 80 個取樣點）。

SMV 主要用於「數位化變電站」，將傳統的類比 CT/VT（電流/電壓互感器）替換為數位感測器。這個領域對一般軟體工程師來說較為特殊，我們在這裡只需了解它的存在即可。

### 三種通訊的定位

```
                    延遲需求
                    │
            < 1ms   │   SMV (取樣值)
                    │   GOOSE (保護信號)
                    │
            < 100ms │
                    │
            < 1s    │   MMS Reports (監控)
                    │
            > 1s    │   MMS Polling (運維)
                    │
                    └─────────────────────
                        資料量
```

## 4. 為什麼 IEC 61850 對儲能/微電網很重要

如果你正在開發儲能系統（ESS）或微電網（Microgrid）的控制軟體，IEC 61850 的重要性正在快速提升。

### 4.1 標準化 DER 模型

IEC 61850-7-420 定義了分散式能源的標準模型。這意味著：

- **PCS 控制** → `DRCS`（DER Controller Supervisor）
- **電池狀態** → `DBAT`（Battery）
- **充放電排程** → `DSCH`（Schedule）
- **量測值** → `MMXU`（Measurement）

無論你整合的是 Sungrow、Huawei 還是 BYD 的 PCS，如果它們都支援 IEC 61850，你就可以用**同一套程式碼**存取同樣的資料路徑。

### 4.2 電網互聯需求

許多國家的電網法規（Grid Code）正在要求 DER 設備支援 IEC 61850。例如：

- 台灣台電的大型儲能案場要求
- 歐洲 EN 50549 系列標準
- 北美 IEEE 2030.5 / IEEE 1547（與 IEC 61850 有映射關係）

### 4.3 保護功能整合

微電網的保護系統需要毫秒級的反應速度。GOOSE 提供了這個能力，而 Modbus 做不到。當電網故障需要立即斷開併網斷路器時，GOOSE 信號可以在 1ms 內到達所有相關設備。

## 5. 與 Modbus 方法的比較

讓我們把兩種方法做一個系統性的比較：

### 5.1 自描述資料模型 vs 平面暫存器地圖

```
# Modbus：你需要一份文件告訴你每個地址是什麼
# register_map_sungrow_pcs.xlsx
# Address | Name          | Type    | Unit | Scale
# 40001   | active_power  | Float32 | kW   | 0.1
# 40003   | reactive_power| Float32 | kVar | 0.1
# 40005   | soc           | UInt16  | %    | 0.1

# IEC 61850：資料模型本身就是文件
# MyPCS/CTRL/MMXU1.TotW.mag.f    → 有功功率 (kW)
# MyPCS/CTRL/MMXU1.TotVAr.mag.f  → 無功功率 (kVar)
# MyPCS/CTRL/DBAT1.Vol.mag.f     → 電池電壓 (V)
```

### 5.2 語義命名 vs 地址數字

| 面向 | Modbus | IEC 61850 |
|------|--------|-----------|
| 識別方式 | 地址 40001 | `MMXU1.TotW.mag.f` |
| 自描述 | 無 | 路徑即語義 |
| 跨廠商一致性 | 每家不同 | 標準化名稱 |
| 資料型別 | 需要文件 | 模型內建 |
| 品質資訊 | 無 | 每個值都有品質標誌 |
| 時間戳記 | 無 | 每個值都有時間戳記 |
| 瀏覽能力 | 無 | 支援 GetDirectory |

### 5.3 實務考量

但 IEC 61850 也有其挑戰：

| 面向 | Modbus | IEC 61850 |
|------|--------|-----------|
| 實作複雜度 | 極低 | 高 |
| 開源支援 | 極豐富 | 有限 |
| 設備支援 | 幾乎所有 | 中高階設備 |
| 網路需求 | 串口 / TCP | TCP + Layer 2 |
| 授權費用 | 免費 | 標準文件需購買 |
| 學習曲線 | 平緩 | 陡峭 |

在實務中，大多數系統採用**混合架構**：底層用 Modbus 與設備通訊，上層用 IEC 61850 與電力調度系統對接。

## 6. csp_lib 的模式如何對應到 IEC 61850 概念

雖然 csp_lib 目前是一個 Modbus 為主的框架，但它的設計模式其實已經暗含了許多 IEC 61850 的設計理念。讓我們來看這些對應關係。

### 6.1 EquipmentTemplate ≈ Logical Device Template

IEC 61850 的 Logical Device 定義了一組相關的 Logical Node。csp_lib 的 `EquipmentTemplate` 同樣定義了一組相關的讀寫點位：

```python
from csp_lib.equipment.template import EquipmentTemplate
from csp_lib.equipment.core import ReadPoint, WritePoint, PointMetadata
from csp_lib.modbus import Float32, UInt16

# csp_lib 的 EquipmentTemplate 就像 IEC 61850 的 Logical Device 定義
pcs_template = EquipmentTemplate(
    model="SUN2000-100KTL",
    always_points=(
        # 類似 IEC 61850 的 MMXU1.TotW.mag.f
        ReadPoint(
            name="active_power",
            address=40001,
            data_type=Float32(),
            metadata=PointMetadata(unit="kW", description="有功功率"),
        ),
        # 類似 IEC 61850 的 MMXU1.TotVAr.mag.f
        ReadPoint(
            name="reactive_power",
            address=40003,
            data_type=Float32(),
            metadata=PointMetadata(unit="kVar", description="無功功率"),
        ),
        # 類似 IEC 61850 的 DBAT1.SOC.mag.f
        ReadPoint(
            name="soc",
            address=40005,
            data_type=UInt16(),
            metadata=PointMetadata(unit="%", description="電池荷電狀態"),
        ),
    ),
    write_points=(
        # 類似 IEC 61850 的 DRCS1.DERCtlP.setMag.f
        WritePoint(
            name="p_set",
            address=41001,
            data_type=Float32(),
            metadata=PointMetadata(unit="kW", description="有功功率設定"),
        ),
    ),
    description="Sungrow 100kW PCS",
)
```

### 6.2 ReadPoint ≈ Data Attribute with Transform

IEC 61850 的 Data Attribute 不只有值，還有品質和時間戳記。csp_lib 的 `ReadPoint` 搭配 `ProcessingPipeline` 提供了類似的概念——原始值經過轉換後才是有意義的工程值：

```python
from csp_lib.equipment.core import ReadPoint, ScaleTransform, RoundTransform
from csp_lib.equipment.core.pipeline import ProcessingPipeline
from csp_lib.modbus import UInt16

# IEC 61850: MMXU1.PhV.phsA.cVal.mag.f (A相電壓)
# 在 IEC 61850 中，值的轉換是模型內建的
# 在 csp_lib 中，我們用 Pipeline 達到同樣效果

voltage_point = ReadPoint(
    name="voltage_a",
    address=40010,
    data_type=UInt16(),
    pipeline=ProcessingPipeline(
        steps=(
            ScaleTransform(magnitude=0.1, offset=0),   # raw * 0.1 → V
            RoundTransform(decimals=1),                  # 保留一位小數
        ),
    ),
)

# raw register = 3801 → 3801 * 0.1 = 380.1V
```

### 6.3 Capability / Trait ≈ Logical Node Classification

這是最精彩的對應。IEC 61850 用 Logical Node 分類設備功能（`MMXU` = 量測、`XCBR` = 斷路器、`DRCS` = DER 控制）。csp_lib 用 `Capability` 做同樣的事：

```python
# csp_lib 的 Capability 系統在概念上類似 IEC 61850 的 Logical Node
from csp_lib.equipment.device.capability import (
    Capability,
    CapabilityBinding,
    ACTIVE_POWER_CONTROL,
    MEASURABLE,
    SOC_READABLE,
)

# ACTIVE_POWER_CONTROL ≈ IEC 61850 的 DRCS (DER Controller)
# MEASURABLE ≈ IEC 61850 的 MMXU (Measurement)
# SOC_READABLE ≈ IEC 61850 的 DBAT (Battery)

# Sungrow PCS 的能力綁定
sungrow_bindings = (
    # 有功功率控制能力：寫入 p_set，讀取 active_power
    CapabilityBinding(
        capability=ACTIVE_POWER_CONTROL,
        point_map={"p_setpoint": "p_set", "p_measurement": "active_power"},
    ),
    # 量測能力：讀取有功功率
    CapabilityBinding(
        capability=MEASURABLE,
        point_map={"active_power": "active_power"},
    ),
    # SOC 讀取能力
    CapabilityBinding(
        capability=SOC_READABLE,
        point_map={"soc": "soc"},
    ),
)

# Huawei PCS — 同樣的能力，不同的點位名稱
huawei_bindings = (
    CapabilityBinding(
        capability=ACTIVE_POWER_CONTROL,
        point_map={"p_setpoint": "pwr_setpoint", "p_measurement": "pwr_actual"},
    ),
    CapabilityBinding(
        capability=MEASURABLE,
        point_map={"active_power": "pwr_actual"},
    ),
    CapabilityBinding(
        capability=SOC_READABLE,
        point_map={"soc": "battery_soc"},
    ),
)
```

Capability 的精髓在於：**Controller 不需要知道具體的點位名稱**。它只需要問設備「你有沒有 ACTIVE_POWER_CONTROL 這個能力？」，然後透過 `resolve()` 方法取得實際的點位名稱。這跟 IEC 61850 的 Logical Node 概念異曲同工。

### 對應總覽

| IEC 61850 概念 | csp_lib 概念 | 說明 |
|----------------|--------------|------|
| Server | 物理設備連線（IP + Port + UnitID）| 通訊端點 |
| Logical Device | `EquipmentTemplate` | 功能模型定義 |
| Logical Node | `Capability` | 功能分類與語義插槽 |
| Data Object | `ReadPoint` / `WritePoint` | 資料存取定義 |
| Data Attribute | 經過 `Pipeline` 轉換後的值 | 最終工程值 |
| SCL 檔案 | Template + Binding 組合 | 設備配置描述 |

## 7. 整合模式：IEC 61850 Gateway → Modbus → csp_lib

在實務中，你很少需要直接實作 IEC 61850 協定堆疊（那是非常複雜的工作）。更常見的架構是透過**協定閘道器（Gateway）**來橋接：

### 典型架構

```
                    ┌──────────────────────┐
                    │   電力調度 / SCADA    │
                    │   (IEC 61850 MMS)    │
                    └────────┬─────────────┘
                             │ MMS
                    ┌────────▼─────────────┐
                    │   IEC 61850 Gateway   │
                    │   (協定轉換)           │
                    └────────┬─────────────┘
                             │ Modbus TCP
                    ┌────────▼─────────────┐
                    │   csp_lib EMS        │
                    │   (能源管理系統)       │
                    └────────┬─────────────┘
                             │ Modbus TCP/RTU
              ┌──────────────┼──────────────┐
              ▼              ▼              ▼
         ┌─────────┐   ┌─────────┐   ┌─────────┐
         │   PCS   │   │  電表    │   │  逆變器  │
         └─────────┘   └─────────┘   └─────────┘
```

### Gateway 的角色

Gateway 負責兩個方向的轉換：

**向上（→ SCADA）**：
- 將 csp_lib 設備的 `latest_values` 映射為 IEC 61850 Data Object
- 將 csp_lib 的 `alarm_triggered` 事件轉換為 IEC 61850 Report
- 將設備連線狀態映射為 Logical Node 的品質標誌

**向下（→ 設備）**：
- 將 IEC 61850 的控制命令轉換為 csp_lib 的 `device.write()` 呼叫
- 將 IEC 61850 的排程轉換為策略參數更新

### 為什麼 csp_lib 的設計讓 Gateway 整合更容易

1. **事件驅動架構**：csp_lib 的 `DeviceEventEmitter` 提供了 `value_change`、`alarm_triggered` 等事件，Gateway 可以直接訂閱這些事件來產生 IEC 61850 Report

2. **Capability 抽象**：Gateway 可以透過 Capability 來自動建立 IEC 61850 的 Logical Node 映射，而不需要硬編碼每個設備的點位名稱

3. **EquipmentTemplate 元資料**：Template 中的 `PointMetadata`（unit、description）可以直接用於建立 IEC 61850 的 Data Object 定義

```python
# 概念性的 Gateway 映射
# csp_lib 的 Capability → IEC 61850 Logical Node

IEC61850_MAPPING = {
    "active_power_control": "DRCS",  # DER Controller
    "measurable": "MMXU",            # Measurement
    "soc_readable": "DBAT",          # Battery
    "switchable": "XCBR",            # Circuit Breaker
    "frequency_measurable": "MMXU",  # Measurement (frequency)
}

# 當 csp_lib 設備有 ACTIVE_POWER_CONTROL capability 時，
# Gateway 就知道要建立對應的 DRCS Logical Node
```

## 8. 重點整理與下篇預告

### 本篇重點

1. **IEC 61850 不只是協定，更是語義資料模型**。它定義了 Server → Logical Device → Logical Node → Data Object → Data Attribute 的階層結構

2. **三種通訊機制各司其職**：MMS 用於一般監控與控制、GOOSE 用於毫秒級保護信號、SMV 用於高速取樣值

3. **語義命名 vs 地址數字**：IEC 61850 的 `MMXU1.TotW.mag.f` 比 Modbus 的「暫存器 40001」攜帶了更多資訊

4. **csp_lib 的設計已暗含 IEC 61850 的理念**：
   - `EquipmentTemplate` ≈ Logical Device
   - `Capability` ≈ Logical Node
   - `ReadPoint` + Pipeline ≈ Data Attribute + Transform

5. **實務中採用 Gateway 橋接**：大多數系統不需要直接實作 IEC 61850，而是透過閘道器在不同層級間轉換

### 給後端工程師的建議

如果你是第一次接觸 IEC 61850，不要被它的複雜度嚇到。把它想成：

- **Server** = 微服務實例
- **Logical Device** = 服務中的功能模組
- **Logical Node** = 模組中的功能介面
- **Data Object** = API 的資源（Resource）
- **Data Attribute** = 資源的屬性欄位

你平時寫的 REST API 或 GraphQL Schema，其實跟 IEC 61850 的資料模型有異曲同工之妙。
